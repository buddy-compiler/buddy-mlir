# EmbeddingGemma

[google/embeddinggemma-300m](https://huggingface.co/google/embeddinggemma-300m)
sentence embeddings, served through the `buddy-cli` / `.rax` runtime. The build
imports the PyTorch SentenceTransformer pipeline, compiles the fixed-shape
forward graph to MLIR, links `embeddinggemma_model.so`, and packs an
`embeddinggemma.rax` manifest plus an `InferenceRunner` plugin that `buddy-cli`
loads at run time.

The compiled kernel is the full SentenceTransformer pipeline traced as a single
AOT graph: Gemma3TextModel encoder -> mean pooling over the real tokens -> dense
768->3072 -> dense 3072->768 -> L2 normalization. The runner tokenizes the input
text and emits the L2-normalized 768-dim embedding vector.

## Prerequisites

- A built LLVM/MLIR and `buddy-mlir` (see the top-level [README](../../README.md)),
  configured with `-DBUDDY_MLIR_ENABLE_PYTHON_PACKAGES=ON`.
- The Python environment that `buddy-mlir` was built against, with `torch`,
  `transformers`, `sentence_transformers`, and the Buddy Python frontend
  available for model import and HF golden generation. The packaged `.rax`
  has no Python dependency for inference.
- A local HuggingFace `google/embeddinggemma-300m` snapshot directory.

## Build

`embeddinggemma` is wired through `buddy_add_model(MODEL_KIND single_forward)`
with its own importer/manifest generator
(`codegen/import-embeddinggemma.py` /
`codegen/gen_embeddinggemma_manifest.py`). It is gated behind the
`BUDDY_BUILD_EMBEDDINGGEMMA_MODEL` CMake option:

```bash
cd buddy-mlir
source buddy-env/bin/activate

cmake -G Ninja -S . -B build \
  -DCMAKE_BUILD_TYPE=Release \
  -DBUDDY_MLIR_ENABLE_PYTHON_PACKAGES=ON \
  -DBUDDY_BUILD_EMBEDDINGGEMMA_MODEL=ON \
  -DBUDDY_EMBEDDINGGEMMA_MODEL_PATH=/path/to/embeddinggemma-300m
cmake --build build --target embeddinggemma_rax
```

`-DBUDDY_EMBEDDINGGEMMA_MODEL_PATH` must point to a local HuggingFace-format
snapshot (it is staged into the build and forwarded to the importer via the
`EMBEDDINGGEMMA_MODEL_PATH` environment variable).

`BUDDY_EMBEDDINGGEMMA_SPEC` selects the fixed-shape spec. The default
`specs/f32.json` uses F32, `max_seq_len = 128`, and `batch_size = 1` when that
field is absent. Changing batch size or sequence length requires rebuilding
the model. For RISC-V builds, configure the toolchain and runtime using
[CrossCompilingRaxFile.md](../../docs/CrossCompilingRaxFile.md), then build
EmbeddingGemma with the CMake target above.

For an A100 scheduling candidate, add `"target_cpu": "spacemit-a100"` to a
copy of the workload spec and build with that spec, using
`BUDDY_RISCV_VLEN=1024`. The importer sets the standard MLIR
`llvm.target_cpu` function attribute, which also reaches the outlined OpenMP
functions. The lowering passes, F32 precision and weights stay the same.
Omitting `target_cpu` preserves the default build. This option does not add
IME kernels or force top-down scheduling. Validate the candidate against the
same HF reference before accepting its K3 performance results.

The importer uses the existing `eliminate_transpose` transform to export
pretransposed F32 Linear weights and remove their runtime transposes.
Use the weights and model library from the same build.

The model's `codegen/lower_to_obj.sh` uses the existing BLIS-style matmul
vectorization pass and canonicalizes loops just before OpenMP conversion.
This removes one-trip parallel loops and combines nested parallel loops, so B1
work is distributed over a useful dimension. Thread selection remains at
runtime through `OMP_NUM_THREADS`; the build does not fix it to one thread.
BLIS-style blocking is generated by Buddy and needs no external BLIS library.
Before bufferization, `linalg-fold-into-elementwise` folds Q/K transposes
into elementwise consumers' indexing maps, avoiding intermediate transpose
buffers while preserving the named MatMul and BatchMatMul paths.
Remaining Linalg operations use the standard affine lowering. Disabling VIR
reduced first-forward latency by 10.27% for B1/S128 and 11.08% for B4/S512 on
SpacemiT K3 A100 (F32, VLEN=1024, four threads at 1.8 GHz), with bit-identical
exported embeddings in these cases. The BLIS and BatchMatMul RVV paths remain
enabled.
GELU's F32 `tanh` uses the existing MLIR polynomial approximation before
affine lowering. This changes F32 rounding; validate final embeddings against
HF with the existing thresholds.
Running `cse` before loop canonicalization exposes redundant copies for
removal while preserving the matrix vectorization paths.
As in the other BLIS model pipelines, `affine-loop-fusion` is omitted: its
combination with the BLIS rewrite produced non-finite embeddings for this graph.
Attention BatchMatMul uses the existing `batchmatmul-optimize` pass with
32-element vectors. F32 accumulation order and FMA rounding can differ, so
validate final embeddings against the same HF golden before accepting
performance results. This build includes the earlier parallel-loop changes.
After canonicalization folds conditional deallocations,
`optimize-allocation-liveness` releases temporary buffers after their last
use without changing the floating-point operations.

The build emits these artifacts under `build/models/embeddinggemma/`:

| File | Description |
| --- | --- |
| `embeddinggemma.rax` | Model manifest (embeds weights, `embeddinggemma_model.so`, `tokenizer.json`, runner) |
| `embeddinggemma_model.so` | Compiled MLIR kernels (exports `_mlir_ciface_forward`) |
| `embeddinggemma_runner.so` | `InferenceRunner` plugin loaded by `buddy-cli` |
| `arg0.data` | Flattened model weights (307,581,953 f32 elements, ~1.2 GB) |
| `tokenizer.json` | Gemma byte-level BPE tokenizer, staged from the local snapshot |

## K3 Transformer Linear IME (optional)

`specs/k3_fp16_comp3.json` selects the K3 A100 matrix-engine path.
The default `specs/f32.json` keeps the F32 path. Configure a separate RISC-V
build directory with VLEN 1024 and Zfh/Zvfh enabled, following
[CrossCompilingRaxFile.md](../../docs/CrossCompilingRaxFile.md), then select:

```bash
EG_IME_BUILD_DIR=/path/to/configured-riscv-ime-build
cmake -S . -B "$EG_IME_BUILD_DIR" \
  -DBUDDY_BUILD_EMBEDDINGGEMMA_MODEL=ON \
  -DBUDDY_EMBEDDINGGEMMA_MODEL_PATH="$EMBEDDINGGEMMA_MODEL_PATH" \
  -DBUDDY_EMBEDDINGGEMMA_SPEC="$PWD/models/embeddinggemma/specs/k3_fp16_comp3.json"
cmake --build "$EG_IME_BUILD_DIR" --target embeddinggemma_rax
```

The importer captures the same complete F32 model, then replaces exactly the
168 encoder projections (72 FFN gate/up/down and 96 Attention Q/K/V/O) with
external kernel calls. It reuses the existing K3 FP16 matrix loop.
Attention QK/PV, GELU, pooling, the two final dense
projections and normalization retain F32 precision. This path
requires `batch_size * max_seq_len` to be divisible by 8; the representative
128/256/512-token workloads satisfy this requirement.

Precision `fp16_comp3` means two FP16 components per operand, three matrix
products, and F32 accumulation, combination and output:
`high*high + 2^-11 * (low*high + high*low)`. Each operand uses a data-dependent
power-of-two scale; low components store the residual multiplied by 2^11.
FP16 subnormals are explicitly flushed while preserving signed zero, matching
the measured native IME path. The result is rescaled in F32. This changes
numerics relative to F32 and must pass the existing embedding validation.

Static weights are split and packed offline. The high and low FP16 components
have the same combined byte count as the original F32 weights. As in YOLOv8,
they are stored as raw bytes in F32 parameter slots; those slots are byte
containers, not F32 arithmetic values. `arg0.data`, the forward ABI, manifest
and runner interface keep their existing sizes and types. Always use the
weights and code from the same build: F32 and IME files have equal sizes but
different layouts.

`embeddinggemma_ime.mlir` contains the wrappers and reused matrix loop. The
existing `kernels_ime` pipeline compiles it for A100 separately; the model's
lowering script joins the objects with the target relocatable linker. F32
code keeps its current compilation options. This variant does not use TCM,
DMA or a different thread pool. `OMP_NUM_THREADS` still selects the threads
at runtime.

The Linear wrappers visit M tiles within each N tile, allowing consecutive
tiles on a worker to reuse the same packed weight block. This changes only
tile traversal, preserving each output's accumulation order. A separate
four-core B1/S128 A-B-A-B comparison (six measured forwards per variant)
reduced median latency from 456.23 to 408.03 ms (10.57%). The full-length input
and four padded inputs remained bit-identical to the previous traversal and
passed the original HF gate. Other batch/sequence sizes require board validation.

Before bufferization, the importer converts the Linear calls to explicit
caller-allocated outputs. The kernels write these buffers and return no
memref. This makes ownership visible to the existing allocation-liveness
pass, allowing early release without runtime checks for aliases of opaque
return values. The top-level forward and runner ABI remain unchanged.

Validate against the original HF/F32 golden for the same inputs, using the
existing `validate_accuracy.py` and `benchmark.py` workflow below. For IME
measurements pass `--spec specs/k3_fp16_comp3.json` (with the actual path) and
`--configuration optimized`; the report records precision `fp16_comp3`.
Keep the F32 baseline labeled `f32`: comparisons between these two variants
are comparisons across precisions. Accept performance results only after the
unchanged cosine and maximum-absolute-error gates pass on the K3.

Complete-RAX acceptance on four A100 cores/threads (B1/S128, 128 valid
tokens, A-B-A-B, one warmup and three measured forwards per group) gave median
latency 870.17 ms for the previous FFN-only `fp16_comp3` path and 545.73 ms
with all encoder Linear projections on IME, a 37.29% reduction. The comparison
uses the same four-core placement. It changes precision coverage: the previous
Attention projections used F32 and now use the compensated FP16 policy.
Peak process RSS was 1344.66 MiB and 1344.51 MiB respectively, including model
loading and runtime rather than isolated kernel workspace.
The full-length input and four padded short inputs passed the original HF
gate; maximum absolute error was 5.07e-7. Repeated outputs within each
configuration were bit-identical. Other
batch/sequence combinations still require complete-RAX board acceptance.

The optional path also fuses all 145 encoder RMSNorms (97 token-wise norms of
width 768 and 48 Q/K head norms of width 256) using the existing K3 F32 RVV
normalization body. Gemma's parameter-only `weight + 1` is folded offline in
F32. Q/K normalization runs before the head-axis permutation and restores that
permutation afterward: each row is still normalized along its last dimension.
The matcher requires the expected shape, permutation and reduction axis.
Final embedding L2 normalization retains its existing lowering. Vector FMA and
reduction change F32 rounding, so final embedding validation remains required.
In a separate B1/S128 A-B-A-B comparison, extending the 97 fused token norms to
all 145 norms reduced median latency from 473.22 to 456.54 ms (3.53%). Peak
process RSS was comparable (1344.70 and 1344.50 MiB). All 24 complete forwards,
including four padded inputs, passed the original HF gate; maximum candidate
error was 5.07e-7 and repeated outputs within each configuration were
bit-identical. Other batch/sequence combinations still require board validation.

## Run

```bash
./build/bin/buddy-cli \
  --model ./build/models/embeddinggemma/embeddinggemma.rax \
  --prompt "The quick brown fox jumps over the lazy dog"
```

- `--prompt "<text>"` selects the text to embed.
- `--prompt-file <file>` supplies one text per line. For a compiled batch of
  size B, supply exactly B lines and pass `--batch-size B`. A batch is executed
  by one forward call; `--batch-size` must match the compiled model.
- `--no-stats` suppresses runner logs and prints only the embedding vector.

The output is a JSON array of 768 values for B=1, or B arrays of 768 values
for a larger batch. Every row is an L2-normalized embedding.

## Baseline measurements

On the K3's Linux/riscv64 system, `benchmark.py` uses the native runner and
GNU `time` to collect embedding latency, sequences/s, tokens/s, batches/s,
and peak process RSS. It requires Python 3.10 or newer and NumPy. Use it to
measure baseline and optimized Buddy builds with the same settings. Original
HF/SentenceTransformer outputs serve as the correctness golden for both builds.
HF preparation may run offline on the build host; performance measurements run
directly on the K3.

`--backend buddy` is the default. `--backend hf` measures the original local
SentenceTransformer on the same K3, using its PyTorch CPU backend in F32.
Both backends start a fresh child process per request and time only its first
complete forward after loading and tokenization. HF uses inference mode,
disables KV cache, and retains its supported default Attention implementation.
Pooling, both Dense modules and final L2 normalization are included. JSON
serialization and correctness checks are outside the timed interval.

Prepare the workload matrix once, using a new output directory. The supplied
corpus generates distinct texts for batch sizes 1, 2 and 4, at effective
lengths of 128, 256 and 512 tokens including BOS/EOS, with no padding.
`matrix.json` lists the generated specs and text files. The following example
selects B2/S128; repeat it with each matrix entry for the full baseline:

```bash
export EMBEDDINGGEMMA_MODEL_PATH=/path/to/embeddinggemma-300m
EG_WORKLOAD_DIR="$PWD/build/embeddinggemma-workloads"
python models/embeddinggemma/prepare_workloads.py \
  --model-path "$EMBEDDINGGEMMA_MODEL_PATH" \
  --output-dir "$EG_WORKLOAD_DIR"

EG_CASE=f32-b2-s128
EG_SPEC="$EG_WORKLOAD_DIR/$EG_CASE.json"
EG_REFERENCE_DIR="$EG_WORKLOAD_DIR/reference-$EG_CASE"
HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 OMP_NUM_THREADS=4 \
python models/embeddinggemma/validate_accuracy.py --mode reference \
  --spec "$EG_SPEC" \
  --texts-file "$EG_WORKLOAD_DIR/$EG_CASE-texts.json" \
  --output-dir "$EG_REFERENCE_DIR"
```

Retain these inputs and golden outputs for both baseline and optimization
runs. Configure an existing RISC-V CMake build for this spec, build the model,
and save the baseline package before applying optimizations:

```bash
EG_BUILD_DIR=/path/to/configured-riscv-build
cmake -S . -B "$EG_BUILD_DIR" \
  -DBUDDY_BUILD_EMBEDDINGGEMMA_MODEL=ON \
  -DBUDDY_EMBEDDINGGEMMA_MODEL_PATH="$EMBEDDINGGEMMA_MODEL_PATH" \
  -DBUDDY_EMBEDDINGGEMMA_SPEC="$EG_SPEC"
cmake --build "$EG_BUILD_DIR" --target embeddinggemma_rax

EG_CONFIGURATION=baseline
EG_RAX="$EG_WORKLOAD_DIR/$EG_CASE-baseline.rax"
cp --no-clobber "$EG_BUILD_DIR/models/embeddinggemma/embeddinggemma.rax" "$EG_RAX"
```

Copy the saved package, its matching workload spec and HF reference directory,
the RISC-V `buddy-cli`, and `benchmark.py` / `validate_accuracy.py` to the K3.
Keep the two Python scripts together; the commands below use their repository
paths. HF/PyTorch packages are only needed on the build host for reference
generation unless measuring `--backend hf`; that backend needs native
PyTorch, Transformers and SentenceTransformers on the K3. Use storage with
enough room for the packages and extracted
payloads; `/tmp` may be backed by RAM.

On the K3, set the destination paths and enter AI process mode before starting
the benchmark so its runner threads execute on the A100 cores. Set CPU affinity
for the assigned A100 cores and keep runner stats enabled. Measure with:

```bash
EG_WORKLOAD_DIR=/path/to/embeddinggemma-workloads
EG_CASE=f32-b2-s128
EG_CONFIGURATION=baseline
EG_RAX="$EG_WORKLOAD_DIR/$EG_CASE-$EG_CONFIGURATION.rax"
EG_SPEC="$EG_WORKLOAD_DIR/$EG_CASE.json"
EG_REFERENCE_DIR="$EG_WORKLOAD_DIR/reference-$EG_CASE"
EG_RESULTS_DIR="$EG_WORKLOAD_DIR/results/$EG_CASE"
EG_BUDDY_CLI=/path/to/riscv-buddy-cli

sh -c 'echo 0 > /proc/set_ai_thread && exec "$@"' sh \
python models/embeddinggemma/benchmark.py \
  --model "$EG_RAX" \
  --buddy-cli "$EG_BUDDY_CLI" \
  --target 'SpacemiT K3 A100; VLEN=1024' \
  --configuration "$EG_CONFIGURATION" \
  --spec "$EG_SPEC" \
  --reference-dir "$EG_REFERENCE_DIR" \
  --threads 4 --warmup 1 --repeat 3 --tolerance 1e-5 \
  --timeout 3600 \
  --output-dir "$EG_RESULTS_DIR/$EG_CONFIGURATION"
```

For the HF reference, use the same F32 workload spec, texts and reference
directory. `--model` selects the original local model directory containing
`modules.json`; downloads are disabled. `--hf-python` selects the native HF
Python executable or environment launcher and defaults to the interpreter
running the benchmark. For example, on the K3:

```bash
EG_HF_MODEL=/path/to/original/embeddinggemma-300m
EG_HF_PYTHON=/path/to/native-hf-environment/python

OMP_PROC_BIND=FALSE OPENBLAS_NUM_THREADS=4 \
sh -c 'echo 0 > /proc/set_ai_thread && exec "$@"' sh \
"$EG_HF_PYTHON" models/embeddinggemma/benchmark.py \
  --backend hf --configuration reference \
  --model "$EG_HF_MODEL" --hf-python "$EG_HF_PYTHON" \
  --target 'SpacemiT K3 A100; VLEN=1024' \
  --spec "$EG_SPEC" --reference-dir "$EG_REFERENCE_DIR" \
  --threads 4 --warmup 1 --repeat 3 --tolerance 1e-5 \
  --output-dir "$EG_RESULTS_DIR/hf-reference"
```

Set the same A100 CPU affinity before starting either benchmark. The HF
backend sets PyTorch intra-op and OpenBLAS threads to `--threads`, inter-op
threads to one, and disables OpenMP per-thread binding so the main thread's
mask is not narrowed before pthread BLAS workers are created. It rejects a
parent CPU mask smaller than the requested thread count. Use
`OMP_PROC_BIND=FALSE` before starting the HF parent as well. The report records
HF library versions, Attention configuration, CPU mask and actual BLAS thread
pools; a configuration change between requests fails the measurement.
HF output files retain the `buddy_embedding_*.npy` names so both backends
use the same existing accuracy validator.

After applying an optimization, rebuild the affected compiler components and
the model on the build host. Confirm the relevant import/lowering stages reran.
Save the new package:

```bash
cmake --build "$EG_BUILD_DIR" --target embeddinggemma_rax
EG_CONFIGURATION=optimized
EG_RAX="$EG_WORKLOAD_DIR/$EG_CASE-optimized.rax"
cp --no-clobber "$EG_BUILD_DIR/models/embeddinggemma/embeddinggemma.rax" "$EG_RAX"
```

Copy the optimized package to the K3, set `EG_CONFIGURATION=optimized` and
`EG_RAX="$EG_WORKLOAD_DIR/$EG_CASE-optimized.rax"` there, then repeat the same
measurement command with a fresh output directory.

For frontend Python changes, rebuild the main `build` tree's Python packages
and remove the generated
`$EG_BUILD_DIR/models/embeddinggemma/.buddy_import_done` stamp before rebuilding
the model so the changed frontend is used for a fresh import.

Use fresh package filenames and result directories for each new candidate;
the baseline package remains fixed. For a same-precision comparison, keep
the weights, input texts, B/S, threads, CPU affinity, hardware configuration,
and warmup/repeat counts identical. `--target` records the actual configuration
used by the caller. The script sets `OMP_NUM_THREADS` and disables dynamic
OpenMP thread counts; CPU affinity is inherited from the caller.

Warmup rounds prepare the extracted payload cache and are excluded from the
statistics. Each request starts a new process and reloads the model, so the
embedding latency includes first-call initialization and is not resident-model
steady-state latency. It measures the full compiled forward, including pooling
and normalization, and excludes loading and tokenization. Latency covers the
entire batch. Throughput uses the same forward timing:

```text
batches/s   = 1000 / embedding_latency_ms
sequences/s = batch_size * batches/s
tokens/s    = sum(valid_tokens) * batches/s
```

`valid_tokens` counts attention-mask entries equal to one, including BOS/EOS
and excluding padding. For the prepared full-length workloads, its sum is
`batch_size * sequence_length`.
Peak RSS covers the runner process's entire lifetime, including weights and
temporary data; it is not limited to allocations within the timed forward.

`report.json` records the baseline/optimized configuration, precision or
quantization variant from the spec, RISC-V execution target, thread count,
batch size, sequence length, measurement scopes, and validation status. Each
sample includes raw measurements and latency/throughput mean, median, min,
max and population standard deviation, plus maximum peak RSS. The execution
mode is recorded as `riscv-native`.
`backend` identifies `buddy` or `hf`; HF reports use configuration `reference`
and require an F32 spec. Each invocation measures one selected backend rather
than performing an automatic comparison.
Raw logs and embeddings are kept under
`runs/<round>/`; `warmup/` holds the unmeasured runs. The extracted payloads are
cached under `payload/`. After timing, every measured round is checked by
`validate_accuracy.compare_outputs`; a failed request, missing measurement,
timeout, or numerical mismatch returns a nonzero exit status. A timeout also
terminates the runner process group. No Git metadata or hashes are collected.

Accept a performance result only when `validation_passed` is true. The F32
commands above use cosine similarity > 0.99 and maximum absolute error < 1e-5
for every embedding row. A saved round can also be checked independently:

```bash
python models/embeddinggemma/validate_accuracy.py --mode compare \
  --reference-dir "$EG_REFERENCE_DIR" \
  --buddy-output-dir "$EG_RESULTS_DIR/$EG_CONFIGURATION/runs/000" \
  --tolerance 1e-5
```

Compare `samples[].embedding_latency_ms.median`, throughput medians and
`peak_rss_mib_max` in the baseline and optimized `report.json` files; inspect
the raw runs and standard deviation alongside them. Latency speedup is
`baseline_median_ms / optimized_median_ms`. This baseline uses F32. Future
precision changes need implementation support, matching spec metadata and
accuracy acceptance before performance is accepted; record and distinguish
different precisions explicitly. For an external reference, compare
`HF F32 / Buddy F32` separately from `HF F32 / Buddy fp16_comp3` and label
the latter as a comparison across precision policies. Alternate the
configurations over multiple groups under the same CPU resource budget.
These first-forward throughput values do not measure a resident service's
sustained throughput.

## Notes

- The `.rax` and other artifacts live in the **build** directory
  (`build/models/embeddinggemma/`), not in the source tree.
- The tokenizer used by the runner is a pure-C++ reimplementation
  (`EmbeddinggemmaTokenizer.h`) of the checkpoint's Gemma byte-level BPE over
  the staged `tokenizer.json`; sequences are wrapped in `<bos>` / `<eos>` and
  padded to `max_seq_len` with `<pad>`.
